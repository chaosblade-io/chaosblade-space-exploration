## 整体设计思路
整个风险分析流程采用**分层聚合、逐步收敛**的策略：

```plain
广度扫描 → 拓扑关联 → 算法排序 → 深度分析 → 场景生成
   ↓           ↓           ↓           ↓          ↓
 全量服务    服务关系     TopX筛选    重点服务    可执行方案
```

核心理念是：**先用低成本的规则扫描建立基础风险画像，再用LLM处理需要理解和推理的复杂分析，最终聚焦到真正高风险的服务上进行深度挖掘。**

---

## Phase 1: K8s资源风险规则扫描
### 目标
以服务为单位，扫描其关联的所有K8s资源，识别配置层面的风险点并量化评分。

### 输入
每个服务关联的K8s资源完整配置，包括：Deployment、Service、ConfigMap、Secret、PVC、HPA、PDB等。

### 核心设计
**资源-服务映射关系**：通过label selector、ownerReference等机制，将K8s资源归属到对应的业务服务。例如 `ts-travel-service` 这个服务会关联到同名的Deployment、Service，以及可能的HPA和PDB。

**风险规则分类体系**：

| 规则类别 | 覆盖范围 | 典型规则示例 |
| --- | --- | --- |
| 可用性风险 | 副本数、探针、PDB | 单副本部署、无就绪探针、无PDB保护 |
| 资源风险 | requests/limits | 无资源限制、资源配额过低、内存超卖 |
| 稳定性风险 | 镜像、更新策略 | 使用latest标签、无滚动更新配置 |
| 数据安全风险 | 存储、数据库 | 数据库单副本、本地存储、无持久化 |
| 可扩展性风险 | HPA、资源裕度 | 无HPA、接近资源上限 |


**评分机制**：每条规则有预设的基础分值（如单副本30分、无探针25分），触发后累加到服务的总风险分上。同时记录风险分类，便于后续分析风险构成。

### 输出
每个服务的风险扫描结果，包含：总风险分、触发的规则列表、各类别风险分布、具体的配置证据。

### 设计要点
+ **规则可配置化**：规则以YAML或JSON形式外置，支持动态增删改
+ **证据链完整**：每个风险都附带触发它的具体配置值，便于后续验证和修复
+ **特殊资源识别**：对数据库、消息队列等关键基础设施采用更严格的规则（如数据库单副本的分值高于普通服务）

## Phase 2: 服务拓扑风险分析
### 目标
从微服务调用拓扑的视角，识别架构层面的系统性风险，并将这些风险关联到具体服务。

### 输入
+ 服务调用关系图（带调用指标：QPS、错误率、延迟）
+ 各服务的Phase 1风险分数
+ 服务运行时状态（健康/告警/故障）

### 核心设计
**拓扑风险类型定义**：

| 风险类型 | 识别特征 | 影响范围 |
| --- | --- | --- |
| 瓶颈风险 | 扇入过高（被大量服务依赖） | 该服务故障会导致大面积不可用 |
| 级联风险 | 扇出过高（依赖大量服务） | 任一依赖故障都可能影响该服务 |
| 耦合风险 | 双向调用、循环依赖 | 故障可能在环路中放大 |
| 深度风险 | 调用链过长（>5跳） | 延迟累积、故障定位困难 |
| 共享风险 | 多服务共享同一数据库/缓存 | 基础设施故障影响多个业务 |
| 孤岛风险 | 无调用关系的服务 | 可能是僵尸服务或监控盲区 |


**LLM分析策略**：

+ 提供完整的拓扑数据（不做截断），让LLM能看到全貌
+ 同时提供统计摘要（最大扇入/扇出、平均调用深度等），帮助LLM快速定位关注点
+ 要求LLM输出结构化结果，每个风险必须关联到具体的服务列表

**分数累加逻辑**：拓扑风险的分数会累加到所有关联服务上。例如识别出"ts-basic-service扇入过高"这个风险（30分），则这30分会加到ts-basic-service的累计风险分上。

### 输出
+ 拓扑层面的风险列表（每个风险包含：名称、描述、严重程度、分数、关联服务）
+ 更新后的服务风险分数（Phase 1分数 + Phase 2分数）

### 设计要点
+ **分析边界清晰**：LLM只负责识别拓扑架构风险，不重复分析资源配置问题
+ **服务关联强制**：prompt中明确要求每个风险必须指明影响哪些服务，避免泛泛而谈
+ **架构洞察**：除了具体风险，也要求LLM给出对整体架构的评价，作为参考信息

## Phase 3: RiskRank 算法排序
### 目标
综合考虑服务的固有风险和风险传播效应，计算出服务的最终风险排名。

### 输入
+ 各服务的累计风险分数（Phase 1 + Phase 2）
+ 服务调用关系及权重（调用频率、错误率、延迟）

### 核心设计
**算法思想**：借鉴PageRank的思路，但进行针对性调整：

| 维度 | PageRank | RiskRank |
| --- | --- | --- |
| 传播方向 | 链接指向 = 重要性传递 | 调用依赖 = 风险传递（被依赖方的风险传递给依赖方） |
| 初始值 | 均匀分布 | 固有风险分数（非均匀） |
| 边权重 | 通常等权 | 调用频率 × 错误率敏感系数 |
| 目标 | 找最重要的节点 | 找风险最高的节点 |


**风险传播逻辑**：

+ 如果服务A调用服务B，那么B的风险会部分传递给A（因为B挂了A也会受影响）
+ 传播强度与调用权重正相关：调用越频繁、错误率越高，风险传递越强
+ 通过迭代计算收敛到稳定的风险分布

**阻尼因子设计**：

+ 设置阻尼因子（如0.85），平衡固有风险和传播风险的权重
+ 固有风险占比 = 1 - 阻尼因子 = 15%
+ 传播风险占比 = 阻尼因子 = 85%
+ 可根据实际场景调整这个比例

**风险贡献分析**：除了计算最终排名，还可以分析每个服务的风险来源构成——多少来自自身配置问题，多少来自依赖的服务。

### 输出
+ 服务风险排名列表（按RiskRank分数降序）
+ 每个服务的风险来源分解（固有风险占比、主要风险贡献者）

### 设计要点
+ **权重参数可调**：边权重的计算公式中，各因子的系数应该支持配置和调优
+ **收敛性保证**：设置最大迭代次数和收敛阈值，确保算法能够终止
+ **结果可解释**：不仅给出排名，还要能解释为什么某个服务排名靠前

## Phase 4: TopX服务Trace深度分析
### 目标
针对RiskRank排名靠前的服务，分析其实际运行时的链路表现，发现前两阶段未能识别的动态风险。

### 输入
+ TopX服务列表及其已识别的风险
+ 与这些服务相关的Trace数据

### 核心设计
**Trace筛选策略**：不是随机选取Trace，而是有优先级地筛选：

| 优先级 | Trace特征 | 分析价值 |
| --- | --- | --- |
| 高 | 包含错误的Trace | 直接暴露故障模式 |
| 高 | 延迟P99以上的Trace | 暴露性能瓶颈 |
| 中 | 调用链较长的Trace | 可能存在级联问题 |
| 低 | 正常Trace | 作为基准对比 |


**分析维度**：

1. **错误模式识别**：Trace中出现的错误类型、频率、分布位置，是否与已识别的K8s资源风险相关（如单副本导致的连接失败）
2. **性能瓶颈定位**：该服务在调用链中的耗时占比，是否存在N+1查询、慢SQL等问题
3. **级联影响评估**：该服务的异常如何向上游传播，影响了哪些调用方
4. **隐藏风险发现**：Trace中暴露但前两阶段未识别的问题，如：特定接口的高错误率、间歇性超时等

**结果与已有风险的关联**：分析结果要尽量与Phase 1/2识别的风险建立关联，形成完整的风险证据链。例如：Trace中发现连接超时 → 可能与"数据库单副本"风险相关。

### 输出
+ 每个TopX服务的Trace分析报告
+ 新发现的运行时风险（补充到服务的风险列表中）
+ 风险关联图谱（哪些运行时表现印证了哪些配置风险）

### 设计要点
+ **聚焦而非全量**：只分析TopX服务相关的Trace，控制LLM调用成本
+ **上下文携带**：分析时把已识别的风险作为背景信息提供给LLM，引导其寻找关联
+ **增量补充**：Phase 4发现的新风险可以补充到服务的风险画像中

## Phase 5: 综合分析与故障场景生成
### 目标
将三层风险信息（资源层、拓扑层、链路层）综合起来，进行关联分析，并生成可执行的混沌工程故障场景。

### 输入
针对每个TopX服务：

+ Phase 1: K8s资源风险列表
+ Phase 2: 拓扑架构风险列表
+ Phase 4: 链路运行时风险列表
+ Phase 3: 风险来源分析

### 核心设计
**风险关联分析**：识别风险之间的因果关系，区分根因风险和衍生风险。

示例关联模式：

+ 单副本部署(DEPLOY_001) → 扇入瓶颈风险(TOPO_003) → 链路错误集中(TRACE_001)
+ 无资源限制(DEPLOY_002) → 延迟尖刺(TRACE_002) → 上游超时(TRACE_003)

**故障场景设计原则**：

| 原则 | 说明 |
| --- | --- |
| 风险驱动 | 每个场景都针对具体的已识别风险 |
| 渐进式 | 从轻微故障开始，逐步加大强度 |
| 可观测 | 明确的成功/失败判定标准 |
| 可回滚 | 有清晰的故障终止和恢复方案 |
| 覆盖全面 | 不同故障类型（资源、网络、应用）都要涉及 |


**场景类型映射**：

| 识别的风险 | 建议的故障场景 |
| --- | --- |
| 单副本部署 | Pod Kill / Pod 故障 |
| 无资源限制 | CPU/内存压力注入 |
| 扇入瓶颈 | 流量放大 / 并发压测 |
| 数据库依赖 | 数据库延迟 / 连接池耗尽 |
| 网络调用链长 | 网络延迟 / 丢包注入 |


**改进建议优先级**：基于风险严重程度和修复成本，给出优先级排序的改进建议。

### 输出
针对每个TopX服务：

+ 风险综合评级（CRITICAL/HIGH/MEDIUM/LOW）
+ 主要风险清单（Top 3）及其因果关系
+ 3-5个故障场景设计（包含：目标、步骤、预期影响、成功标准、回滚方案）
+ 改进建议列表（按优先级排序）

全局输出：

+ 执行摘要（整体健康度评分、高危服务数量）
+ 全局性改进建议

### 设计要点
+ **三层融合**：真正把资源、拓扑、链路三层信息综合起来分析，而非简单拼接
+ **可执行性**：故障场景要具体到可以直接转化为ChaosBlade等工具的配置
+ **业务视角**：如果有业务重要性信息，应该纳入优先级考量

## 整体流程协作
```plain
┌─────────────────────────────────────────────────────────────────┐
│                        数据流转关系                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   K8s API ──→ Phase 1 ──→ 服务风险分数 V1                        │
│                              │                                  │
│   服务拓扑 ──→ Phase 2 ──→ 服务风险分数 V2 (累加拓扑风险)          │
│                              │                                  │
│   调用关系 ──→ Phase 3 ──→ RiskRank排名 ──→ TopX服务              │
│                                              │                  │
│   Trace数据 ──→ Phase 4 ──→ 链路风险 ────────┤                   │
│                                              │                  │
│                              Phase 5 ←───────┘                  │
│                                 │                               │
│                                 ▼                               │
│                          综合分析报告                            │
│                          故障场景方案                            │
│                          改进建议清单                            │
└─────────────────────────────────────────────────────────────────┘
```

**成本控制策略**：

+ Phase 1: 纯规则引擎，无LLM成本
+ Phase 2: 1次LLM调用，分析整体拓扑
+ Phase 3: 纯算法，无LLM成本
+ Phase 4: TopX次LLM调用（每个重点服务1次）
+ Phase 5: TopX次LLM调用（每个重点服务1次）

如果TopX=5，总共约11次LLM调用，成本可控。
